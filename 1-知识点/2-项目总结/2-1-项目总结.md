# Apache DolphinScheduler 项目总结

## 一、项目概述

### 1.1 项目简介

Apache DolphinScheduler 是一个分布式、易扩展的可视化 DAG 工作流任务调度系统。致力于解决数据处理流程中错综复杂的依赖关系，使调度系统在数据处理流程中"开箱即用"。

**核心定位**：
- 分布式工作流调度平台
- 可视化 DAG 编排
- 高可用、高性能
- Cloud Native 架构

**技术栈**：
- **语言**：Java 8
- **框架**：Spring Boot 2.6.1
- **注册中心**：ZooKeeper/Etcd
- **数据库**：MySQL/PostgreSQL/H2
- **RPC**：Netty
- **前端**：React + TypeScript

### 1.2 项目规模

- **模块数量**：20+ 个核心模块
- **代码量**：数十万行 Java 代码
- **插件体系**：支持 50+ 任务类型插件
- **部署方式**：Standalone、Cluster、Docker、Kubernetes

### 1.3 核心特性

1. **易于部署**：提供四种部署方式，包括 Standalone、Cluster、Docker 和 Kubernetes
2. **易于使用**：可以通过 Web UI、Python SDK 和 Open API 创建和管理工作流
3. **高可靠高可用**：多主多从的去中心化架构，原生支持横向扩展
4. **高性能**：性能比其他编排平台快 N 倍，每天可支持千万级任务
5. **Cloud Native**：支持编排多云/数据中心工作流，支持自定义任务类型
6. **版本控制**：对工作流和工作流实例（包括任务）进行版本控制
7. **状态控制**：工作流和任务的多种状态控制，支持随时暂停/停止/恢复
8. **多租户支持**：完整的租户隔离和权限控制

## 三、核心亮点

### 3.1 无中心化 Master 集群架构

**设计理念**：所有 Master 节点地位平等，无 Leader 节点，避免单点故障。

**核心机制**：

```mermaid
graph TB
    subgraph "Slot 分片机制"
        A[Master 启动] --> B[注册到 ZooKeeper]
        B --> C[获取所有 Master 列表]
        C --> D[按地址排序]
        D --> E[计算 Slot = 索引位置]
        E --> F[totalSlots = Master 数量]
    end
    
    subgraph "Command 分片获取"
        F --> G[IdSlotBasedCommandFetcher]
        G --> H[SQL: WHERE id % totalSlots = currentSlot]
        H --> I[获取属于当前 Slot 的 Command]
    end
    
    subgraph "动态重平衡"
        J[Master 节点变化] --> K[TreeCache 监听]
        K --> L[MasterSlotManager.doReBalance]
        L --> M[重新计算所有 Slot]
        M --> N[更新 currentSlot 和 totalSlots]
    end
    
    style E fill:#fff4e1
    style H fill:#e8f5e9
    style L fill:#e1f5ff
```

**优势**：
- ✅ **无单点故障**：任意 Master 故障不影响整体服务
- ✅ **水平扩展**：新增 Master 节点即可扩展，无需手动配置
- ✅ **负载均衡**：Slot 机制实现任务均匀分配
- ✅ **自动容错**：节点故障自动检测，Slot 自动重平衡

- ✅ **状态管理**：通过状态机模式管理状态转换

### 3.3 状态机设计

**设计理念**：严格的状态机设计，确保状态流转符合业务逻辑。

**工作流状态机**：

```mermaid
stateDiagram-v2
    [*] --> SUBMITTED_SUCCESS: 工作流创建
    SUBMITTED_SUCCESS --> RUNNING_EXECUTION: 开始执行
    RUNNING_EXECUTION --> SUCCESS: 所有任务成功
    RUNNING_EXECUTION --> FAILURE: 任务失败且不可重试
    RUNNING_EXECUTION --> PAUSE: 暂停操作
    RUNNING_EXECUTION --> STOP: 停止操作
    PAUSE --> RUNNING_EXECUTION: 恢复执行
    STOP --> [*]
    SUCCESS --> [*]
    FAILURE --> [*]
```

**任务状态机**：

```mermaid
stateDiagram-v2
    [*] --> NotInitialized: TaskExecutionRunnable创建<br/>taskInstance = null
    NotInitialized --> SUBMITTED_SUCCESS: initializeFirstRunTaskInstance<br/>创建TaskInstance并插入数据库
    SUBMITTED_SUCCESS --> DISPATCH: TaskDispatchLifecycleEvent<br/>准备分发任务
    DISPATCH --> DISPATCHED: 已发送到Worker<br/>RPC调用成功
    DISPATCHED --> RUNNING_EXECUTION: Worker开始执行<br/>TaskRunningLifecycleEvent
    RUNNING_EXECUTION --> SUCCESS: 任务执行成功<br/>TaskSuccessLifecycleEvent
    RUNNING_EXECUTION --> FAILURE: 任务执行失败<br/>TaskFailedLifecycleEvent
    FAILURE --> SUBMITTED_SUCCESS: retry()<br/>可重试且未达最大次数
    FAILURE --> [*]: 不可重试或达到最大次数
    RUNNING_EXECUTION --> PAUSE: pause()<br/>暂停操作
    PAUSE --> SUBMITTED_SUCCESS: 恢复执行
    RUNNING_EXECUTION --> KILL: kill()<br/>终止操作
    KILL --> [*]
    SUCCESS --> [*]
    
    note right of NotInitialized
        TaskInstance延迟创建
        首次触发时才创建
        避免不必要的数据库写入
    end note
    
    note right of SUBMITTED_SUCCESS
        任务已提交
        等待被Worker接收执行
        支持重试和故障转移
    end note
```

**状态机设计优势**：
- ✅ **严格的状态流转**：每个状态只能转换到允许的下一个状态
- ✅ **事务保证**：状态转换与数据库更新在同一事务中
- ✅ **幂等性**：相同事件多次处理不会导致状态异常
- ✅ **可追溯性**：所有状态变化都有日志记录

### 3.4 乐观锁防重复处理机制

**设计理念**：使用数据库事务删除操作作为分布式锁，避免多 Master 重复处理同一 Command。

**实现机制**：

```mermaid
sequenceDiagram
    participant M1 as Master-1
    participant M2 as Master-2
    participant DB as 数据库
    participant Factory as WorkflowExecutionRunnableFactory
    
    Note over M1,M2: 两个Master同时拉取到同一个Command
    M1->>DB: SELECT * FROM t_ds_command WHERE id = 100
    M2->>DB: SELECT * FROM t_ds_command WHERE id = 100
    DB-->>M1: Command(id=100)
    DB-->>M2: Command(id=100)
    
    Note over M1,Factory: Master-1 开始处理
    M1->>Factory: createWorkflowExecuteRunnable(command)
    Factory->>DB: BEGIN TRANSACTION
    Factory->>DB: DELETE FROM t_ds_command WHERE id = 100
    DB-->>Factory: 删除成功 (affectedRows = 1)
    Factory->>Factory: doCreateWorkflowExecutionRunnable()
    Factory->>DB: COMMIT TRANSACTION
    
    Note over M2,Factory: Master-2 开始处理（稍晚）
    M2->>Factory: createWorkflowExecuteRunnable(command)
    Factory->>DB: BEGIN TRANSACTION
    Factory->>DB: DELETE FROM t_ds_command WHERE id = 100
    DB-->>Factory: 删除失败 (affectedRows = 0)
    Factory->>Factory: throw CommandDuplicateHandleException
    Factory->>DB: ROLLBACK TRANSACTION
    
    Note over M1,M2: 只有Master-1成功处理了Command
```

**优势**：
- ✅ **简单高效**：无需额外的分布式锁组件（如 Redis）
- ✅ **原子性保证**：数据库事务确保操作的原子性
- ✅ **无死锁风险**：删除操作不会导致死锁
- ✅ **自动清理**：Command 处理完成后自动删除，无需手动清理

### 3.6 故障转移机制

**设计理念**：通过延迟检测、分布式锁、状态恢复实现可靠的故障转移。

**故障转移流程**：

```mermaid
flowchart TD

    K --> L[更新工作流状态]
    L --> M[插入恢复命令]
    M --> N[释放分布式锁]
    
    I --> O[TaskFailover.failoverTask]
    O --> P[创建新的任务实例]
```

### 4.2 事件总线实现

**DelayQueue 延迟事件机制**：

```java
// AbstractDelayEventBus
public class AbstractDelayEventBus<T extends AbstractDelayEvent> {
    private final DelayQueue<T> delayEventQueue = new DelayQueue<>();
    
    public void publish(T event) {
        delayEventQueue.offer(event);
    }
    
    public T take() throws InterruptedException {
        return delayEventQueue.take(); // 阻塞等待，直到有元素到期
    }
}

// AbstractDelayEvent
public abstract class AbstractDelayEvent implements Delayed {
    private final Date eventTime;
    private final long delayTime; // 延迟时间（毫秒）
    
    @Override
    public long getDelay(TimeUnit unit) {
        long delay = (eventTime.getTime() + delayTime) - System.currentTimeMillis();
        return unit.convert(delay, TimeUnit.MILLISECONDS);
    }
}
```

### 4.3 ReentrantLock + Condition 实践

**场景一：事件通道等待/唤醒机制**

```java
// TaskExecutorLifecycleEventRemoteReporter
private final Lock eventChannelsLock = new ReentrantLock();
private final Condition taskExecutionEventEmptyCondition = 
    eventChannelsLock.newCondition();

// 报告事件（添加事件到通道）
public void reportTaskExecutorLifecycleEvent(...) {
    eventChannelsLock.lock();
    try {
        eventChannels.computeIfAbsent(...).addTaskExecutionEvent(event);
        taskExecutionEventEmptyCondition.signalAll(); // 唤醒等待线程
    } finally {
        eventChannelsLock.unlock();
    }
}

// 等待所有通道为空
private void tryToWaitIfAllTaskExecutionEventChannelEmpty() 
        throws InterruptedException {
    eventChannelsLock.lock();
    try {
        while (isAllTaskExecutorEventChannelEmpty()) {
            taskExecutionEventEmptyCondition.await(); // 自动释放锁，等待唤醒
        }
    } finally {
        eventChannelsLock.unlock();
    }
}
```

**优势**：
- ✅ **避免忙等待**：使用 `Condition.await()` 让线程进入 WAITING 状态
- ✅ **精确控制**：可以精确控制等待时间
- ✅ **自动锁管理**：`await()` 自动释放锁，被唤醒后自动重新获取

### 4.4 双重检查锁定模式

**NettyRemotingClient Channel 创建**：

```java
private final ReentrantLock channelsLock = new ReentrantLock();
private final Map<Host, Channel> channels = new ConcurrentHashMap<>();

Channel getOrCreateChannel(Host host) {
    // 第一次检查（无锁，快速路径）
    Channel channel = channels.get(host);
    if (channel != null && channel.isActive()) {
        return channel;
    }
    
    try {
        channelsLock.lock();
        // 第二次检查（有锁，避免重复创建）
        channel = channels.get(host);
        if (channel != null && channel.isActive()) {
            return channel;
        }
        // 创建新 Channel
        channel = createChannel(host);
        channels.put(host, channel);
    } finally {
        channelsLock.unlock();
    }
    return channel;
}
```

**优势**：
- ✅ **性能优化**：第一次检查无锁，避免不必要的锁竞争
- ✅ **线程安全**：双重检查确保不会重复创建 Channel
- ✅ **资源节约**：复用已存在的 Channel

### 5.2 问题二：网络抖动导致误触发故障转移

**问题描述**：
- 网络暂时中断可能导致节点在注册中心短暂消失
- 触发故障转移，但节点实际未故障

**解决方案**：30秒延迟机制

- ✅ 给节点足够时间重新连接
- ✅ 减少不必要的故障转移开销

### 5.3 问题三：Worker 事件丢失导致状态不一致

**问题描述**：
- Worker 端事件存储在内存中（DelayQueue、ConcurrentHashMap）
- Worker 重启会导致事件丢失
- Master 和 Worker 同时故障可能导致状态不一致

**解决方案**：最终一致性 + 故障转移机制

```mermaid

    C --> D[更新数据库状态]
    D --> E[Worker故障检测]
    E --> F[Worker故障转移]
    F --> G[创建新任务实例]
    G --> H[重新分发任务]
    
    B -->|否| I[Master和Worker都故障]
    I --> J[Master恢复]
    J --> K[全局故障转移]
    K --> L[从数据库恢复状态]
    L --> M[重建WorkflowExecutionRunnable]
    M --> N[检查Worker是否存活]
    N --> O{Worker存活?}
    O -->|否| F
    O -->|是| P[继续执行或重新分发]
    
    style I fill:#ffebee
    style K fill:#e8f5e9
    style F fill:#fff4e1
```

**设计权衡**：
- ✅ **性能优先**：事件存储在内存中，保证高性能
- ✅ **最终一致性**：通过重试机制和故障转移，尽可能保证最终一致性
- ✅ **可接受的数据丢失**：在极端情况下可能存在少量状态不一致，但可以通过监控和运维手段发现并修复

### 5.4 问题四：Slot 重平衡导致任务分配变化

**问题描述**：
- Master 集群变化时，Slot 会重新分配
- 可能导致正在处理的 Command 分配发生变化

**解决方案**：已获取的 Command 不受影响

```mermaid

```

**关键点**：
- ✅ 已获取的 Command 已在数据库中删除（事务保证）
- ✅ 正在处理的 Command 不受影响
- ✅ 新 Command 会按照新的 Slot 分配

## 六、设计思路总结

### 6.1 去中心化设计思路

**核心理念**：无 Leader 节点，所有 Master 地位平等

**实现方式**：
1. **Slot 分片**：每个 Master 处理固定分片的 Command
2. **动态重平衡**：集群变化时自动调整 Slot 分配
3. **一致性视图**：通过 ZooKeeper TreeCache 保证所有节点看到相同的集群视图

**优势**：
- 无单点故障
- 水平扩展
- 负载均衡

### 6.2 事件驱动设计思路

**核心理念**：通过事件总线实现组件解耦

**实现方式**：
1. **事件发布**：组件发布事件到事件总线
2. **事件处理**：工作线程轮询事件并处理
3. **状态机**：通过状态机模式管理状态转换

**优势**：
- 解耦设计
- 异步处理
- 易于扩展

### 6.3 插件化设计思路

**核心理念**：通过 SPI 机制实现插件化架构

**实现方式**：
1. **SPI 接口**：定义统一的插件接口
2. **ServiceLoader**：Java SPI 机制加载插件
3. **优先级支持**：支持插件优先级，解决冲突

**优势**：
- 高度可扩展
- 热插拔
- 统一接口

### 6.4 容错设计思路

**核心理念**：通过延迟检测、分布式锁、状态恢复实现可靠容错

**实现方式**：
1. **延迟检测**：30秒延迟避免误触发
2. **分布式锁**：防止重复故障转移
3. **状态恢复**：从数据库恢复状态

**优势**：
- 避免误触发
- 自动恢复
- 状态一致性

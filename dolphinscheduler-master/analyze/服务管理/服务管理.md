## 1. 服务注册 Zookeeper

### 1.1 注册入口

Master 服务启动时，在 `MasterServer.start()` 方法中调用注册：

### 1.2 注册流程详解

#### 步骤 1: MasterRegistryClient.start()

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/registry/MasterRegistryClient.java:62`

```java
public void start() {
    try {
        // 1. 创建心跳任务实例（此时还未启动）
        this.masterHeartBeatTask =
                new MasterHeartBeatTask(masterConfig, metricsProvider, registryClient, masterCoordinator);
        
        // 2. 执行注册
        registry();
        
        // 3. 添加连接状态监听器
        registryClient.addConnectionStateListener(new MasterConnectionStateListener(registryClient));
    } catch (Exception e) {
        throw new RegistryException("Master registry client start up error", e);
    }
}
```

**关键点：**
- 先创建 `MasterHeartBeatTask` 实例，但此时还未启动
- 调用 `registry()` 执行实际注册
- 注册完成后添加连接状态监听器

#### 步骤 2: registry() 方法详解

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/registry/MasterRegistryClient.java:93`

```java
void registry() {
    log.info("Master node : {} registering to registry center", masterConfig.getMasterAddress());
    String masterRegistryPath = masterConfig.getMasterRegistryPath();
    
    // 步骤 2.1: 等待服务状态为 NORMAL
    MasterHeartBeat heartBeat = masterHeartBeatTask.getHeartBeat();
    while (ServerStatus.BUSY.equals(heartBeat.getServerStatus())) {
        log.warn("Master node is BUSY: {}", heartBeat);
        heartBeat = masterHeartBeatTask.getHeartBeat();
        ThreadUtils.sleep(SLEEP_TIME_MILLIS);  // 等待 1 秒
    }
    
    // 步骤 2.2: 删除旧节点（如果存在）
    registryClient.remove(masterRegistryPath);
    
    // 步骤 2.3: 创建 EPHEMERAL 节点
    registryClient.persistEphemeral(masterRegistryPath, JSONUtils.toJsonString(masterHeartBeatTask.getHeartBeat()));
    log.info("Master node persisted to registry path: {}, host: {}", masterRegistryPath, NetUtils.getHost());
    
    // 步骤 2.4: 验证节点是否成功创建（最多重试 30 次）
    int checkCount = 0;
    while (!registryClient.checkNodeExists(NetUtils.getHost(), RegistryNodeType.MASTER)) {
        checkCount++;
        log.warn("The current master server node:{} cannot find in registry, check count: {}, registry path: {}", 
                NetUtils.getHost(), checkCount, masterRegistryPath);
        ThreadUtils.sleep(SLEEP_TIME_MILLIS);
        if (checkCount > 30) {
            log.error("Master node:{} cannot be found in registry after {} checks", NetUtils.getHost(), checkCount);
            throw new RegistryException("Master node cannot be found in registry after multiple checks");
        }
    }
    log.info("Master node:{} found in registry after {} checks", NetUtils.getHost(), checkCount);
    
    // 步骤 2.5: 等待 1 秒，确保 Master Failover 清理完成
    ThreadUtils.sleep(SLEEP_TIME_MILLIS);
    
    // 步骤 2.6: 启动心跳任务
    masterHeartBeatTask.start();
    log.info("Master node : {} registered to registry center successfully", masterConfig.getMasterAddress());
}
```

**详细说明：**

1. **等待服务状态为 NORMAL**
    - 如果服务状态为 BUSY（负载过高），等待直到变为 NORMAL
    - 避免在服务繁忙时注册

2. **删除旧节点**
    - 如果之前注册过，先删除旧节点
    - 确保节点数据是最新的

3. **创建 EPHEMERAL 节点**
    - 调用 `persistEphemeral()` 创建临时节点
    - 节点路径：`/nodes/master/{masterAddress}`
    - 节点数据：MasterHeartBeat 的 JSON 字符串

4. **验证节点创建**
    - 循环检查节点是否存在
    - 最多重试 30 次，每次等待 1 秒
    - 如果 30 次后仍未找到，抛出异常

5. **等待 Failover 清理**
    - 等待 1 秒，确保之前的 Failover 标记已清理

6. **启动心跳任务**
    - 启动 `MasterHeartBeatTask`，开始定期更新心跳

#### 步骤 3: persistEphemeral() 实现

**代码位置：** `dolphinscheduler-registry/dolphinscheduler-registry-plugins/dolphinscheduler-registry-zookeeper/src/main/java/org/apache/dolphinscheduler/plugin/registry/zookeeper/ZookeeperRegistry.java:172`

```java
@Override
public void put(String key, String value, boolean deleteOnDisconnect) {
    final CreateMode mode = deleteOnDisconnect ? CreateMode.EPHEMERAL : CreateMode.PERSISTENT;
    
    try {
        client.create()
                .orSetData()                    // 如果节点已存在，则更新数据
                .creatingParentsIfNeeded()     // 自动创建父节点
                .withMode(mode)                // 设置节点类型（EPHEMERAL 或 PERSISTENT）
                .forPath(key, value.getBytes(StandardCharsets.UTF_8));
    } catch (Exception e) {
        throw new RegistryException("Failed to put registry key: " + key, e);
    }
}
```

**关键点：**

1. **`orSetData()`**
    - 如果节点已存在，则更新数据
    - 如果节点不存在，则创建新节点

2. **`creatingParentsIfNeeded()`**
    - 自动创建父节点
    - 例如：创建 `/nodes/master/192.168.1.100:5678` 时，如果 `/nodes` 和 `/nodes/master` 不存在，会自动创建

3. **`withMode(CreateMode.EPHEMERAL)`**
    - 创建临时节点
    - 当客户端会话断开时，节点会自动删除

#### 步骤 4: 父节点自动创建机制

**工作原理：**

```
完整路径：/nodes/master/192.168.1.100:5678

Curator 解析路径：
  1. /nodes                    → 检查是否存在，不存在则创建
  2. /nodes/master             → 检查是否存在，不存在则创建
  3. /nodes/master/192.168.1.100:5678  → 创建 EPHEMERAL 节点

如果父节点已存在：
  - 直接使用，不重复创建
  - 只创建目标节点
```

**代码实现：**

CuratorFramework 内部实现：
- 解析路径，按 `/` 分割
- 从根路径开始，逐级检查父节点是否存在
- 如果不存在，创建父节点（PERSISTENT 类型）
- 最后创建目标节点（EPHEMERAL 类型）

### 1.4 集群 vs 单机注册

#### 相同点

1. **注册机制完全相同**
    - 都使用 `MasterRegistryClient.registry()` 方法
    - 都创建 EPHEMERAL 节点
    - 都启动心跳任务

2. **注册路径格式相同**
    - 都是 `/nodes/master/{masterAddress}`
    - 每个 Master 有唯一的路径

3. **心跳机制相同**
    - 都使用 `MasterHeartBeatTask` 更新心跳
    - 心跳间隔都是 10 秒（可配置）

#### 不同点

**集群模式：**
```
Zookeeper 节点结构：
  /nodes/master/
    ├── 192.168.1.100:5678  (Master-A)
    ├── 192.168.1.101:5678  (Master-B)
    └── 192.168.1.102:5678  (Master-C)
```

**单机模式：**
```
Zookeeper 节点结构：
  /nodes/master/
    └── 192.168.1.100:5678  (Master-A)
```

**区别：**
- 集群模式：多个 Master 节点注册到同一父路径下
- 单机模式：只有一个 Master 节点注册

## 2. 脑裂问题以及解决方案

### 2.1 什么是脑裂问题

**脑裂（Split-Brain）**：在分布式系统中，当网络分区或节点故障时，不同部分的集群认为自己是主节点，导致数据不一致。

**典型场景：**
```
初始状态：
  Master-A ←→ Zookeeper ←→ Master-B
  Master-A ←→ Master-B

网络分区后：
  Master-A ←→ Zookeeper  (Master-A 认为自己是主节点)
  Master-B              (Master-B 无法连接 Zookeeper，但仍在运行)
  
结果：
  - Master-A 和 Master-B 都认为自己是主节点
  - 可能同时调度同一任务
  - 导致数据不一致
```

### 2.2 脑裂问题的危害

#### 危害 1: 数据不一致

**场景示例：**

```
时间线：
T1: Master-A 和 Master-B 都连接到 Zookeeper
  - 工作流 Workflow-1 被 Master-A 调度执行

T2: 网络分区
  - Master-A 与 Zookeeper 断开
  - Master-B 仍连接到 Zookeeper

T3: Master-A 继续运行（未停止）
  - Master-A 认为自己是主节点
  - 继续调度任务

T4: Master-B 也调度 Workflow-1
  - 因为 Master-A 的节点被删除，Master-B 认为需要容错
  - 重新调度 Workflow-1

结果：
  - Workflow-1 被两个 Master 同时执行
  - 数据库状态混乱
  - 任务可能重复执行
```

#### 危害 2: EPHEMERAL 节点失效

**场景示例：**

```
时间线：
T1: Master-A 注册到 Zookeeper
  - 节点：/nodes/master/192.168.1.100:5678
  - 类型：EPHEMERAL

T2: Master-A 与 Zookeeper 断开连接
  - Zookeeper 会话超时（60 秒）
  - EPHEMERAL 节点被删除

T3: 其他 Master 感知到节点删除
  - 认为 Master-A 已下线
  - 触发 Failover

T4: Master-A 仍在运行（未停止）
  - Master-A 不知道自己的节点已被删除
  - 继续执行任务

结果：
  - 其他 Master 认为 Master-A 已下线
  - Master-A 认为自己仍在运行
  - 状态不一致
```

#### 危害 3: 脏数据

**场景示例：**

```
时间线：
T1: Master-A 正常上报心跳
  - reportTime = T1
  - 数据写入 Zookeeper

T2: Master-A 网络断开（第 7 秒）
  - 无法上报新心跳
  - Zookeeper 中的节点数据仍然是 T1 时刻的旧数据

T3: Master-B 读取 Master-A 的信息
  - 读取到旧数据（reportTime = T1，已过时 7 秒）
  - 基于过时信息做决策

T4: Master-B 基于过时信息操作失败
  - 任务调度失败
  - 需要容错机制恢复
```

### 2.3 DolphinScheduler 的解决方案

#### 方案 1: 主动停止服务（主要机制）

**核心思想：** 当 Master 与 Zookeeper 断开连接时，**主动停止服务**，避免脑裂。

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/registry/MasterConnectionStateListener.java:36`

```java
@Override
public void onUpdate(ConnectionState state) {
    log.info("Master received a {} event from registry, the current server state is {}", state,
            ServerLifeCycleManager.getServerStatus());
    switch (state) {
        case CONNECTED:
            // 连接成功，不做处理
            break;
        case SUSPENDED:
            // 连接暂停，不做处理
            break;
        case RECONNECTED:
            // 重新连接，记录日志
            log.warn("Master reconnect to registry");
            break;
        case DISCONNECTED:
            // 连接断开，主动停止服务
            registryClient.getStoppable().stop("Master disconnected from registry, will stop myself");
            break;
        default:
            log.warn("Unknown connection state: {}", state);
    }
}
```

**工作原理：**

```
1. Zookeeper 客户端心跳失败（底层 PING 失败）
   ↓
2. 60 秒后（sessionTimeout），Zookeeper 会话超时
   ↓
3. CuratorFramework 触发 LOST 状态
   ↓
4. ZookeeperConnectionStateListener 转换为 DISCONNECTED
   ↓
5. MasterConnectionStateListener 收到事件
   ↓
6. 调用 registryClient.getStoppable().stop()
   ↓
7. Master 服务主动停止
```

**状态转换链：**

```
Zookeeper 会话超时
    ↓
CuratorFramework.ConnectionState.LOST
    ↓
ZookeeperConnectionStateListener.stateChanged()
    ↓
ConnectionState.DISCONNECTED
    ↓
MasterConnectionStateListener.onUpdate()
    ↓
registryClient.getStoppable().stop()
    ↓
MasterServer.stop()
    ↓
服务停止
```

**优势：**

1. **避免脑裂**
    - 断开连接时立即停止，不会继续运行
    - 不会与其他 Master 产生冲突

2. **保证一致性**
    - EPHEMERAL 节点被删除，其他节点立即感知
    - 状态一致

3. **防止脏数据**
    - 无法通信时停止服务，避免产生过时数据
    - 其他节点不会读取到过时信息

#### 方案 2: EPHEMERAL 节点自动删除

**工作原理：**

```
Master 与 Zookeeper 断开连接
    ↓
Zookeeper 会话超时（60 秒）
    ↓
Zookeeper 服务端自动删除 EPHEMERAL 节点
    ↓
其他 Master 通过 TreeCache 监听到节点删除
    ↓
触发 REMOVE 事件
    ↓
触发 Failover 机制
```

**代码位置：** `dolphinscheduler-registry/dolphinscheduler-registry-plugins/dolphinscheduler-registry-zookeeper/src/main/java/org/apache/dolphinscheduler/plugin/registry/zookeeper/ZookeeperRegistry.java:142`

```java
@Override
public void subscribe(final String path, final SubscribeListener listener) {
    final TreeCache treeCache = treeCacheMap.computeIfAbsent(path, $ -> new TreeCache(client, path));
    treeCache.getListenable().addListener(new ZookeeperTreeCacheListenerAdapter(path, listener));
    try {
        treeCache.start();
    } catch (Exception e) {
        treeCacheMap.remove(path);
        throw new RegistryException("Failed to subscribe listener for key: " + path, e);
    }
}
```

**TreeCache 监听机制：**
- TreeCache 监听整个路径树的变化
- 当节点被删除时，触发 `NODE_REMOVED` 事件
- 转换为 DolphinScheduler 的 `REMOVE` 事件

#### 方案 3: 分布式锁

**MasterCoordinator 使用分布式锁选举 Active Master：**

**代码位置：** `dolphinscheduler-registry/dolphinscheduler-registry-api/src/main/java/org/apache/dolphinscheduler/registry/api/ha/AbstractHAServer.java:94`

```java
@Override
public boolean participateElection() {
    final String electionLock = selectorPath + "-lock";
    // If meet exception during participate election, will retry.
    // This can avoid the situation that the server is not elected as leader due to network jitter.
    for (int i = 0; i < DEFAULT_MAX_RETRY_TIMES; i++) {
        try {
            try {
                // 1. 获取分布式锁
                if (registry.acquireLock(electionLock)) {
                    // 2. 检查选择器路径是否存在
                    if (!registry.exists(selectorPath)) {
                        // 3. 如果不存在，创建节点并写入自己的标识
                        registry.put(selectorPath, serverIdentify, true);
                        return true;  // 选举成功，成为 Active
                    }
                    // 4. 如果已存在，检查是否是自己
                    return serverIdentify.equals(registry.get(selectorPath));
                }
                return false;  // 获取锁失败
            } finally {
                // 5. 释放分布式锁
                registry.releaseLock(electionLock);
            }
        } catch (Exception e) {
            log.error("Participate election error, meet an exception, will retry after {}ms",
                    DEFAULT_RETRY_INTERVAL, e);
            ThreadUtils.sleep(DEFAULT_RETRY_INTERVAL);
        }
    }
    throw new IllegalStateException(
            "Participate election failed after retry " + DEFAULT_MAX_RETRY_TIMES + " times");
}
```

**选举流程：**

```
1. 获取分布式锁（electionLock）
   ↓
2. 检查选择器路径是否存在
   ↓
3a. 如果不存在：
    - 创建节点，写入自己的标识
    - 返回 true（成为 Active）
   ↓
3b. 如果已存在：
    - 读取节点数据
    - 如果是自己，返回 true（保持 Active）
    - 如果不是自己，返回 false（保持 Standby）
   ↓
4. 释放分布式锁
```

**重试机制：**
- 最多重试 20 次（`DEFAULT_MAX_RETRY_TIMES`）
- 每次重试间隔 5 秒（`DEFAULT_RETRY_INTERVAL`）
- 避免网络抖动导致的选举失败

**MasterCoordinator 使用示例：**


- 只有一个 Master 成为 Active
- Active Master 运行 `TaskGroupCoordinator`
- 其他 Master 为 Standby，不运行 `TaskGroupCoordinator`

### 3.4 连接状态详解

#### CuratorFramework 连接状态

CuratorFramework 定义了以下连接状态：

| Curator 状态 | 说明 | 触发条件 |
|-------------|------|---------|
| `CONNECTED` | 已连接 | 成功连接到 Zookeeper |
| `RECONNECTED` | 重新连接 | 断开后重新连接成功 |
| `SUSPENDED` | 连接暂停 | 连接暂时中断，但会话仍有效 |
| `LOST` | 连接丢失 | 会话超时，连接永久丢失 |

#### 状态转换

**代码位置：** `dolphinscheduler-registry/dolphinscheduler-registry-plugins/dolphinscheduler-registry-zookeeper/src/main/java/org/apache/dolphinscheduler/plugin/registry/zookeeper/ZookeeperConnectionStateListener.java:37`

```java
@Override
public void stateChanged(CuratorFramework client,
                         org.apache.curator.framework.state.ConnectionState newState) {
    switch (newState) {
        case CONNECTED:
            log.info("Registry connected");
            listener.onUpdate(ConnectionState.CONNECTED);
            break;
        case LOST:
            log.warn("Registry disconnected");
            listener.onUpdate(ConnectionState.DISCONNECTED);  // LOST 转换为 DISCONNECTED
            break;
        case RECONNECTED:
            log.info("Registry reconnected");
            listener.onUpdate(ConnectionState.RECONNECTED);
            break;
        case SUSPENDED:
            log.warn("Registry suspended");
            listener.onUpdate(ConnectionState.SUSPENDED);
            break;
        default:
            break;
    }
}
```

**状态转换链：**

```
正常连接：
  CONNECTED → (网络抖动) → SUSPENDED → RECONNECTED → CONNECTED

会话超时：
  CONNECTED → (网络断开) → SUSPENDED → (60秒超时) → LOST → DISCONNECTED
```

### 3.5 底层心跳机制

#### Zookeeper 客户端心跳（底层）

**工作原理：**

```
1. CuratorFramework 客户端启动后，自动维护与 Zookeeper 的会话
   ↓
2. Zookeeper 客户端每 1/3 sessionTimeout 发送一次心跳（PING）
   - sessionTimeout = 60秒
   - 心跳频率 ≈ 每 20 秒一次
   ↓
3. Zookeeper 服务端收到心跳后，更新会话的 lastProcessedZxid
   ↓
4. 如果 60 秒内没有收到心跳，会话超时
   ↓
5. Zookeeper 服务端删除该会话的所有 EPHEMERAL 节点
```

**心跳特点：**
- **自动管理**：由 Zookeeper 客户端自动发送，无需应用层代码
- **频率固定**：约为 sessionTimeout 的 1/3
- **目的单一**：仅用于维持会话有效性，不包含业务数据

#### 与应用层心跳的区别

| 特性 | 底层心跳（Zookeeper 客户端） | 应用层心跳（MasterHeartBeatTask） |
|------|---------------------------|--------------------------------|
| **频率** | 约每 20 秒（自动） | 每 10 秒（可配置） |
| **目的** | 维持会话有效性 | 更新节点数据 |
| **数据** | 无数据（PING） | 包含服务器状态、资源使用等 |
| **超时** | 60 秒 | 不超时（持续更新） |
| **触发** | 会话超时后删除 EPHEMERAL 节点 | 更新节点数据 |

### 3.7 重试策略详解

#### ExponentialBackoffRetry（指数退避重试）

**配置参数：**
- `baseSleepTime`：1 秒（基础睡眠时间）
- `maxRetries`：5 次（最大重试次数）
- `maxSleep`：3 秒（最大睡眠时间）

**重试逻辑：**

```
第 1 次重试：睡眠 1 秒
第 2 次重试：睡眠 2 秒（1 * 2）
第 3 次重试：睡眠 3 秒（min(2 * 2, 3) = 3）
第 4 次重试：睡眠 3 秒（min(3 * 2, 3) = 3）
第 5 次重试：睡眠 3 秒（min(3 * 2, 3) = 3）
```

**应用场景：**
- 创建节点失败
- 获取数据失败
- 更新数据失败
- 删除节点失败

- 例如：操作 `/nodes/master` 实际路径为 `/dolphinscheduler/nodes/master`

**优势：**
- 隔离不同应用的数据

### 4.3 心跳更新逻辑

#### BaseHeartBeatTask.run()

**代码位置：** `dolphinscheduler-common/src/main/java/org/apache/dolphinscheduler/common/model/BaseHeartBeatTask.java:52`

```java
@Override
public void run() {
    while (runningFlag) {
        try {
            // 1. 获取当前心跳数据
            T heartBeat = getHeartBeat();
            
            // 2. 判断是否需要写入
            // 条件1：距离上次写入时间 >= 心跳间隔（10秒）
            // 条件2：服务器状态改变（NORMAL ↔ BUSY）
            if (System.currentTimeMillis() - lastWriteTime >= heartBeatInterval
                    || !lastHeartBeat.getServerStatus().equals(heartBeat.getServerStatus())) {
                lastHeartBeat = heartBeat;
                writeHeartBeat(heartBeat);
                lastWriteTime = System.currentTimeMillis();
            }
        } catch (Exception ex) {
            log.error("{} task execute failed", threadName, ex);
        } finally {
            try {
                // 3. 每 1 秒扫描一次
                Thread.sleep(DEFAULT_HEARTBEAT_SCAN_INTERVAL);  // 1 秒
            } catch (InterruptedException e) {
                handleInterruptException(e);
            }
        }
    }
}
```

**更新逻辑：**

```
循环执行（每 1 秒）：
  1. 获取当前心跳数据
  2. 判断是否需要写入：
     - 距离上次写入时间 >= 10秒  OR
     - 服务器状态改变（NORMAL ↔ BUSY）
  3. 如果需要写入：
     - 更新 lastHeartBeat
     - 调用 writeHeartBeat()
     - 更新 lastWriteTime
  4. 睡眠 1 秒，继续循环
```

**更新频率：**
- **扫描频率**：每 1 秒扫描一次
- **写入频率**：每 10 秒写入一次（或状态改变时立即写入）

### 4.4 心跳数据过时处理

#### 问题场景

```
时间线：
T0 (0s): Master-A 正常上报心跳
  - reportTime = T0
  - 数据写入 Zookeeper

T1 (7s): Master-A 出现问题（网络断开/服务繁忙）
  - 无法上报新心跳
  - Zookeeper 中的节点数据仍然是 T0 时刻的旧数据

T2 (7s): Master-B 读取 Master-A 的信息
  - 读取到旧数据（reportTime = T0，已过时 7 秒）
  - 可能基于过时信息做决策
  - 可能导致操作失败
```

#### 容错机制

**机制 1: Zookeeper EPHEMERAL 节点自动删除**

```
如果 Master-A 在第 7 秒断开：
  - Zookeeper 客户端心跳失败（底层 PING 失败）
  - 60 秒后（T0 + 67秒），Zookeeper 会话超时
  - Zookeeper 服务端自动删除 EPHEMERAL 节点
  - 其他节点立即收到 REMOVE 事件
  - 触发 Failover 机制
```

**机制 2: 操作失败时的容错**

```
当基于过时信息操作失败时：
  - 重试机制：任务会被放回队列，等待重试
  - 超时检测：任务执行超时，然后被重新调度
  - Failover 机制：Master 下线后，工作流被重新分配
```

**机制 3: 实时事件监听**

```
Master-B 订阅了 /nodes/master 路径
  - 当 Master-A 的节点被删除时，立即收到 REMOVE 事件
  - 当 Master-A 的节点数据更新时，立即收到 UPDATE 事件
  - 不需要轮询，实时感知变化
```

## 5. 容错产生以及机制

### 5.1 容错触发场景

#### 场景 1: Master 网络断开/服务停止

**完整时间线：**

```
T1 (0s): Master-A 网络断开或服务停止
  - Zookeeper 客户端心跳失败
  - 无法更新心跳数据
  - 但 EPHEMERAL 节点仍然存在

T2 (20s): Zookeeper 客户端尝试 PING
  - 失败（网络仍断开）
  - CuratorFramework 开始重连

T3 (40s): Zookeeper 客户端再次尝试 PING
  - 失败（网络仍断开）
  - 会话即将超时

T4 (60s): Zookeeper 会话超时
  - Zookeeper 服务端删除 EPHEMERAL 节点
  - /nodes/master/192.168.1.100:5678 被删除
  - CuratorFramework 触发 LOST 状态

T5 (60s): Master-A 收到 DISCONNECTED 事件
  - MasterConnectionStateListener.onUpdate(DISCONNECTED)
  - 调用 registryClient.getStoppable().stop()
  - Master-A 主动停止服务

T6 (60s): 其他 Master 监听到 REMOVE 事件
  - Master-B 和 Master-C 的 AbstractClusterSubscribeListener 收到事件
  - 触发 onServerRemove()

T7 (60s): 触发 Failover 事件
  - ClusterStateMonitors.masterRemoved() 被调用
  - 发布 MasterFailoverEvent（延迟 30 秒）

T8 (90s): 执行 Failover
  - FailoverCoordinator.failoverMaster() 被调用
  - 查询数据库，找到 Master-A 负责的工作流
  - 将这些工作流标记为 FAILOVER
  - 创建容错命令
  - 重新分配 Slot，其他 Master 接管
```

#### 场景 2: Master 负载过高执行失败

**时间线：**

```
T1: Master-A 负载过高，任务执行失败
  - 任务状态变为 FAILURE
  - 如果配置了重试，会自动重试

T2: 如果 Master-A 因为负载过高无法继续工作
  - 心跳状态可能变为 BUSY
  - 但节点仍然存在
  - 其他 Master 可以通过心跳数据看到 Master-A 状态为 BUSY

T3: 如果 Master-A 最终崩溃
  - 进程停止
  - 无法发送心跳
  - 回到场景 1 的流程
```

#### 场景 3: Master 正在执行任务时崩溃

**详细流程：**

```
T1: Master-A 正在执行 Workflow-1
  - Workflow-1 状态为 RUNNING
  - 数据库记录：host = '192.168.1.100:5678'
  - 任务 Task-1 状态为 RUNNING

T2: Master-A 崩溃
  - 进程停止
  - 无法更新心跳

T3 (60s): Zookeeper 删除节点
  - 触发 REMOVE 事件

T4 (90s): Failover 执行
  - 查询数据库：host = '192.168.1.100:5678' 且状态为 RUNNING 的工作流
  - 找到 Workflow-1
  - 将 Workflow-1 状态改为 FAILOVER
  - 创建 RECOVER_TOLERANCE_FAULT_PROCESS 命令

T5: 其他 Master 获取命令
  - 通过 Slot 机制，某个 Master 获取到容错命令
  - 重新执行 Workflow-1
  - 从失败的任务开始恢复
```

```java
public void notify(Event event) {
    try {
        // 确保事件按顺序处理
        synchronized (this) {
            Event.Type type = event.getType();
            T server = parseServerFromHeartbeat(event.getEventData());

                    log.warn("Server {} removed", server);

                    onServerUpdate(server);
                    break;
                default:
                    break;
            }
        }
    } catch (Exception ex) {
        log.error("Notify cluster change event: {} failed", event, ex);
    }
}
```

### 5.3 容错处理流程

#### 步骤 1: 查询需要容错的工作流

```java
private List<WorkflowInstance> getFailoverWorkflowsForMaster(final String masterAddress,
                                                             final Date masterCrashTime) {
    // 1. 查询该 Master 负责的所有需要容错的工作流
    final List<WorkflowInstance> workflowInstances =
            workflowInstanceDao.queryNeedFailoverWorkflowInstances(masterAddress);
    
    // 2. 过滤工作流
    return workflowInstances.stream()
            .filter(workflowInstance -> {
                // 过滤条件1：工作流不在内存中（避免重复容错）
                if (workflowRepository.contains(workflowInstance.getId())) {
                    return false;
                }
                
                // 过滤条件2：重启时间在 Master 崩溃时间之前
                final Date restartTime = workflowInstance.getRestartTime();
                if (restartTime != null) {
                    return restartTime.before(masterCrashTime);
                }
                
                // 过滤条件3：启动时间在 Master 崩溃时间之前
                final Date startTime = workflowInstance.getStartTime();
                return startTime.before(masterCrashTime);
            })
            .collect(Collectors.toList());
}
```

**查询条件：**
- `host = masterAddress`（由该 Master 负责）
- 状态为 `RUNNING_EXECUTION` 或 `SUBMITTED_SUCCESS`
- 启动时间在 Master 崩溃时间之前

## 6. 去中心化设计

### 6.1 去中心化 vs 中心化

#### 中心化设计（传统）

**架构特点：**
```
┌─────────────────────────────────────┐
│         Leader Master               │
│  ┌─────────────────────────────┐   │
│  │  处理所有任务调度              │   │
│  │  管理所有工作流                │   │
│  └─────────────────────────────┘   │
└─────────────────────────────────────┘
         │
    ┌────┴────┐
    │         │
┌───▼───┐ ┌───▼───┐
│Standby│ │Standby│
│Master │ │Master │
└───────┘ └───────┘
```

**特点：**
- 有一个 Leader Master
- 其他 Master 是 Standby
- Leader 负责所有任务调度
- Leader 宕机后选举新 Leader

**问题：**
- **单点故障**：Leader 宕机后需要选举，期间服务不可用
- **Leader 过载**：所有任务都由 Leader 处理，可能过载
- **选举影响**：选举过程可能影响服务

#### 去中心化设计（DolphinScheduler）

**架构特点：**
```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│   Master-A   │  │   Master-B   │  │   Master-C   │
│              │  │              │  │              │
│  Slot 0      │  │  Slot 1      │  │  Slot 2      │
│              │  │              │  │              │
│  处理 Command│  │  处理 Command│  │  处理 Command│
│  ID % 3 = 0  │  │  ID % 3 = 1   │  │  ID % 3 = 2   │
└──────────────┘  └──────────────┘  └──────────────┘
       │                 │                 │
       └─────────────────┴─────────────────┘
                    │
            Zookeeper
```

**特点：**
- 所有 Master 地位平等
- 没有 Leader/Standby 之分
- 通过 Slot 机制分配任务
- 每个 Master 负责自己的 Slot

**优势：**
- **无单点故障**：任何 Master 宕机，其他 Master 自动接管
- **自动负载均衡**：任务自动分配到不同 Master
- **节点宕机后自动重新分配**：Slot 自动重新平衡

### 6.2 Slot 机制（去中心化核心）

#### Slot 分配原理详解

**步骤 1: 动态计算 Slot**

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/cluster/MasterSlotManager.java:60`

```java
@Override
public void doReBalance(List<MasterServerMetadata> normalMasterServers) {
    int tmpCurrentSlot = -1;
    
    // 1. 遍历所有正常的 Master 节点
    for (int i = 0; i < normalMasterServers.size(); i++) {
        // 2. 找到当前 Master 在列表中的位置
        if (normalMasterServers.get(i).getAddress().equals(masterConfig.getMasterAddress())) {
            tmpCurrentSlot = i;  // 索引就是 Slot
            break;
        }
    }
    
    // 3. 如果找不到当前 Master，设置为无效
    if (tmpCurrentSlot == -1) {
        log.warn("Do rebalance failed, cannot found the current master: {} in the normal master clusters: {}",
                masterConfig.getMasterAddress(), normalMasterServers);
        currentSlot = -1;
        return;
    }
    
    // 4. 如果 Slot 没有变化，直接返回
    if (totalSlots == normalMasterServers.size() && currentSlot == tmpCurrentSlot) {
        log.debug("No need to rebalance, the currentSlot: {}, totalSlots: {} doesn't changed",
                currentSlot, totalSlots);
        return;
    }
    
    // 5. 更新 Slot 信息
    totalSlots = normalMasterServers.size();
    currentSlot = tmpCurrentSlot;
    log.info("Do rebalance success, current master slot: {}, total master slots: {}", currentSlot, totalSlots);
}
```

**工作原理：**

```
1. 获取所有正常的 Master 节点列表
   - 只包含状态为 NORMAL 的 Master
   - 按地址排序（字典序）
   
2. 找到当前 Master 在列表中的位置（索引）
   - 例如：Master-B 在列表中的位置是 1
   - 那么 Master-B 的 Slot 就是 1
   
3. 更新 Slot 信息
   - currentSlot = 找到的索引
   - totalSlots = 列表大小
```

**详细示例：**

```
假设有 3 个 Master：
  - Master-A: 192.168.1.100:5678
  - Master-B: 192.168.1.101:5678
  - Master-C: 192.168.1.102:5678

排序后（按地址字典序）：
  [0] Master-A (192.168.1.100:5678) → Slot 0
  [1] Master-B (192.168.1.101:5678) → Slot 1
  [2] Master-C (192.168.1.102:5678) → Slot 2

每个 Master 自动知道自己的 Slot：
  - Master-A: currentSlot = 0, totalSlots = 3
  - Master-B: currentSlot = 1, totalSlots = 3
  - Master-C: currentSlot = 2, totalSlots = 3
```

**步骤 2: 基于 Slot 的命令分配**

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/engine/command/IdSlotBasedCommandFetcher.java:57`

```java
    long cost = System.currentTimeMillis() - scheduleStartTime;
    log.debug("[Slot-{}/{}] Fetch {} commands in {}ms.", currentSlotIndex, totalSlot, commands.size(), cost);
```

- **均匀分配**：命令均匀分配到各个 Master
- **确定性**：同一个 Command ID 总是分配给同一个 Slot
- **自动负载均衡**：任务自动分散到不同 Master

### 6.3 MasterCoordinator（单例协调）

#### 为什么需要 MasterCoordinator？

虽然命令分配使用 Slot 机制（去中心化），但某些任务需要**单例执行**：

**需要单例的任务：**
- **TaskGroupCoordinator**：管理全局 TaskGroup 资源
   - 需要统一管理，避免冲突
   - 不能多个 Master 同时管理

**为什么不能使用 Slot 机制？**

```
如果使用 Slot 机制分配 TaskGroup 管理：

Master-A: 管理 TaskGroup ID % 3 = 0 的组
Master-B: 管理 TaskGroup ID % 3 = 1 的组
Master-C: 管理 TaskGroup ID % 3 = 2 的组

问题：
1. 全局状态不一致
   - TaskGroup-1 的 useSize 需要全局一致
   - 如果 Master-A 和 Master-B 同时更新，会冲突

2. 等待队列处理冲突
   - 多个任务等待 TaskGroup-1 的槽位
   - 如果 Master-A 和 Master-B 同时处理，可能分配同一个槽位

3. 资源竞争
   - TaskGroup 槽位是共享资源
   - 需要统一管理，不能分散到多个 Master
```

**选举机制详解：**

**代码位置：** `dolphinscheduler-registry/dolphinscheduler-registry-api/src/main/java/org/apache/dolphinscheduler/registry/api/ha/AbstractHAServer.java:94`

```java
@Override
public boolean participateElection() {
    final String electionLock = selectorPath + "-lock";
    // 如果选举过程中遇到异常，会重试
    // 这可以避免因网络抖动导致服务器未被选为 Leader
    for (int i = 0; i < DEFAULT_MAX_RETRY_TIMES; i++) {
        try {
            try {
                // 1. 获取分布式锁
                if (registry.acquireLock(electionLock)) {
                    // 2. 检查选择器路径是否存在
                    if (!registry.exists(selectorPath)) {
                        // 3. 如果不存在，创建节点并写入自己的标识
                        registry.put(selectorPath, serverIdentify, true);
                        return true;  // 选举成功，成为 Active
                    }
                    // 4. 如果已存在，检查是否是自己
                    return serverIdentify.equals(registry.get(selectorPath));
                }
                return false;  // 获取锁失败
            } finally {
                // 5. 释放分布式锁
                registry.releaseLock(electionLock);
            }
        } catch (Exception e) {
            log.error("Participate election error, meet an exception, will retry after {}ms",
                    DEFAULT_RETRY_INTERVAL, e);
            ThreadUtils.sleep(DEFAULT_RETRY_INTERVAL);
        }
    }
    throw new IllegalStateException(
            "Participate election failed after retry " + DEFAULT_MAX_RETRY_TIMES + " times");
}
```

**选举流程：**

```
1. 获取分布式锁（electionLock = /nodes/master-coordinator-lock）
   ↓
2. 检查选择器路径是否存在（/nodes/master-coordinator）
   ↓
3a. 如果不存在：
    - 创建节点，写入自己的标识（192.168.1.100:5678）
    - 返回 true（成为 Active）
   ↓
3b. 如果已存在：
    - 读取节点数据
    - 如果是自己，返回 true（保持 Active）
    - 如果不是自己，返回 false（保持 Standby）
   ↓
4. 释放分布式锁
```

**状态变化监听：**

```java

                        statusChange(ServerStatus.ACTIVE);
                    }
                }
            }
        }
    });
    
    // 启动时尝试选举

        statusChange(ServerStatus.ACTIVE);
    } else {

    }
}
```

**选举结果：**
- 只有一个 Master 成为 Active
- Active Master 运行 `TaskGroupCoordinator`
- 其他 Master 为 Standby，不运行 `TaskGroupCoordinator`

**选举示例：**

```
初始状态（3 个 Master）：
  Master-A: 尝试选举 → 成功 → Active ✅
  Master-B: 尝试选举 → 失败（Master-A 已存在）→ Standby
  Master-C: 尝试选举 → 失败（Master-A 已存在）→ Standby

Master-A 崩溃后：
  Master-A 的节点被删除
  Master-B: 监听到节点删除 → 尝试选举 → 成功 → Active ✅
  Master-C: 尝试选举 → 失败（Master-B 已存在）→ Standby
```

#### Slot 机制 vs MasterCoordinator

| 特性 | Slot 机制 | MasterCoordinator |
|------|----------|------------------|
| **目的** | 负载均衡分配 | 单例任务管理 |
| **应用场景** | Command 分配 | TaskGroupCoordinator |
| **参与节点** | 所有 Master 都参与 | 只有一个 Active |
| **冲突风险** | 无冲突（各自处理） | 需要单例避免冲突 |
| **选举方式** | 无选举（自动分配） | Leader 选举（分布式锁） |
| **重新平衡** | 自动重新平衡 | 自动重新选举 |

**关系：**
- **互补**：服务于不同场景
- **不冲突**：职责不同
- **协作**：MasterCoordinator 管理全局资源，Slot 机制分配工作负载

### 6.4 TaskGroupCoordinator 详解

#### TaskGroup 的作用

**TaskGroup** 用于控制任务并发数，限制资源压力。

**典型场景：**
```
场景：限制对 Hadoop 集群的并发访问

问题：
  - 有 100 个任务需要访问 Hadoop 集群
  - 如果同时执行，Hadoop 集群会过载
  - 需要限制同时执行的任务数

解决方案：
  - 创建 TaskGroup：Hadoop 资源组
  - 设置 groupSize = 10（最多 10 个任务同时执行）
  - 其他任务等待，直到有槽位释放
```

**TaskGroup 配置：**
- **名称**：TaskGroup 名称
- **资源容量（groupSize）**：允许任务实例并发的最大数量
- **当前使用量（useSize）**：当前正在执行的任务数

#### 职责 3: 处理等待队列（核心功能）

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/engine/TaskGroupCoordinator.java:257`

```java
private void dealWithWaitingTaskGroupQueue() {
    // 1. 查询所有可用的 TaskGroup（状态为启用）
    List<TaskGroup> taskGroups = taskGroupDao.queryAvailableTaskGroups();
    if (CollectionUtils.isEmpty(taskGroups)) {
        log.debug("There is no available task group");
        return;
    }
    
    for (TaskGroup taskGroup : taskGroups) {
        // 2. 计算可用槽位
        int availableSize = taskGroup.getGroupSize() - taskGroup.getUseSize();
        if (availableSize <= 0) {
            log.info("TaskGroup {} is full, available size is {}", taskGroup, availableSize);
            continue;
        }
        
        // 3. 查询等待队列（按优先级排序）
        List<TaskGroupQueue> taskGroupQueues =
                taskGroupQueueDao.queryAllInQueueTaskGroupQueueByGroupId(taskGroup.getId())
                        .stream()
                        .filter(taskGroupQueue -> Flag.NO.getCode() == taskGroupQueue.getForceStart())
                        .filter(taskGroupQueue -> TaskGroupQueueStatus.WAIT_QUEUE == taskGroupQueue.getStatus())
                        .limit(availableSize)  // 只处理可用槽位数量
                        .collect(Collectors.toList());
        
        if (CollectionUtils.isEmpty(taskGroupQueues)) {
            log.debug("There is no waiting task group queue for task group {}", taskGroup.getName());
            continue;
        }
        
        // 4. 为每个等待的任务分配槽位
        for (TaskGroupQueue taskGroupQueue : taskGroupQueues) {
            try {
                // 4.1 获取 TaskGroup 槽位（原子操作）
                boolean acquireResult = taskGroupDao.acquireTaskGroupSlot(taskGroup.getId());
                if (!acquireResult) {
                    log.error("Failed to acquire task group slot for task group {}", taskGroup);
                    continue;
                }
                
                // 4.2 通知等待的任务实例
                notifyWaitingTaskInstance(taskGroupQueue);
                
                // 4.3 更新 TaskGroupQueue 状态
                taskGroupQueue.setStatus(TaskGroupQueueStatus.ACQUIRE_SUCCESS);
                taskGroupQueue.setUpdateTime(new Date());
                taskGroupQueueDao.updateById(taskGroupQueue);
                
                log.info("Success acquire TaskGroupSlot for TaskGroupQueue: {}", taskGroupQueue);
            } catch (Exception e) {
                log.error("Notify Waiting TaskGroupQueue: {} failed", taskGroupQueue, e);
            }
        }
    }
}
```

**处理流程：**

```
1. 查询所有可用的 TaskGroup
   ↓
2. 对每个 TaskGroup：
   a. 计算可用槽位 = groupSize - useSize
   b. 如果可用槽位 <= 0，跳过
   c. 查询等待队列（按优先级排序）
   d. 限制数量为可用槽位数量
   ↓
3. 为每个等待的任务：
   a. 获取 TaskGroup 槽位（原子操作）
   b. 通知任务实例（RPC 调用）
   c. 更新 TaskGroupQueue 状态为 ACQUIRE_SUCCESS
```

```java
@Override
public void acquireTaskGroupSlot(TaskInstance taskInstance) {
    if (taskInstance == null || taskInstance.getTaskGroupId() <= 0) {
        throw new IllegalArgumentException("The current TaskInstance does not use task group");
    }
    
    TaskGroup taskGroup = taskGroupDao.queryById(taskInstance.getTaskGroupId());
    if (taskGroup == null) {
        throw new IllegalArgumentException(
                "The current TaskGroup: " + taskInstance.getTaskGroupId() + " does not exist");
    }
    
    // 创建 TaskGroupQueue 记录，状态为 WAIT_QUEUE
    Date now = new Date();
    TaskGroupQueue taskGroupQueue = TaskGroupQueue
            .builder()
            .taskId(taskInstance.getId())
            .taskName(taskInstance.getName())
            .groupId(taskInstance.getTaskGroupId())
            .workflowInstanceId(taskInstance.getWorkflowInstanceId())
            .priority(taskInstance.getTaskGroupPriority())
            .inQueue(Flag.YES.getCode())
            .forceStart(Flag.NO.getCode())
            .status(TaskGroupQueueStatus.WAIT_QUEUE)  // 等待状态
            .createTime(now)
            .updateTime(now)
            .build();
    
    log.info("Success insert TaskGroupQueue: {} for TaskInstance: {}", taskGroupQueue, taskInstance.getName());
    taskGroupQueueDao.insert(taskGroupQueue);
    
    // 任务进入等待状态，等待 TaskGroupCoordinator 分配槽位
}
```

**完整流程示例：**

```
T1: Master-B 执行 Task-1（需要 TaskGroup-1 槽位）
  - 调用 taskGroupCoordinator.acquireTaskGroupSlot(Task-1)
  - 创建 TaskGroupQueue 记录：
    {
      taskId: 1,
      taskName: "Task-1",
      groupId: 1,
      priority: 5,
      status: WAIT_QUEUE  // 等待状态
    }
  - 插入数据库 t_ds_task_group_queue 表
  - Task-1 进入等待状态，不立即执行

T2: TaskGroupCoordinator（在 Master-A 上）每 5 秒扫描一次
  - 查询 TaskGroup-1：groupSize = 3, useSize = 0
  - availableSize = 3 - 0 = 3（有 3 个可用槽位）
  - 查询等待队列：找到 Task-1 的 TaskGroupQueue
  - 分配槽位：
    a. 调用 taskGroupDao.acquireTaskGroupSlot(1)
    b. TaskGroup-1.useSize 从 0 变为 1
  - 通知任务：
    a. 调用 notifyWaitingTaskInstance(TaskGroupQueue-1)
    b. 发送 RPC 通知 Master-B：Task-1 可以执行了
  - 更新状态：
    a. TaskGroupQueue-1.status = ACQUIRE_SUCCESS

T3: Master-B 收到通知
  - Task-1 获得 TaskGroup-1 槽位
  - Task-1 状态变为 RUNNING
  - 开始执行任务（访问 Hadoop 集群）

T4: 更多任务请求槽位
  - Master-B: Task-2 需要 TaskGroup-1 槽位
  - Master-C: Task-3 需要 TaskGroup-1 槽位
  - Master-A: Task-4 需要 TaskGroup-1 槽位
  - 都创建 TaskGroupQueue，状态为 WAIT_QUEUE

T5: TaskGroupCoordinator 再次扫描
  - TaskGroup-1: useSize = 1, availableSize = 2
  - 分配槽位给 Task-2 和 Task-3
  - TaskGroup-1: useSize = 3（已满）
  - Task-4 继续等待（没有可用槽位）

T6: Task-1 执行完成
  - Master-B 调用 taskGroupCoordinator.releaseTaskGroupSlot(Task-1)
  - 删除 TaskGroupQueue-1
  - TaskGroup-1.useSize 从 3 变为 2

T7: TaskGroupCoordinator 扫描
  - TaskGroup-1: useSize = 2, availableSize = 1
  - 找到等待的 Task-4
  - 分配槽位给 Task-4
  - TaskGroup-1: useSize = 3（再次满）
```

#### 为什么需要单例管理？

**问题场景：如果多个 Master 同时管理**

```
假设 Master-A 和 Master-B 都运行 TaskGroupCoordinator：

T1: TaskGroup-1: useSize = 2, availableSize = 1
  - 等待队列：Task-4, Task-5

T2: Master-A 的 TaskGroupCoordinator 扫描：
  - 发现 availableSize = 1
  - 分配槽位给 Task-4
  - useSize = 3

T3: Master-B 的 TaskGroupCoordinator 同时扫描：
  - 也发现 availableSize = 1（读取到的是旧数据）
  - 分配槽位给 Task-5
  - useSize = 4（超过了 groupSize = 3！）

结果：
  - TaskGroup-1 的并发数超过了限制
  - Hadoop 集群可能过载
  - 资源控制失效
```

**单例管理的优势：**

```
只有 Master-A（Active）运行 TaskGroupCoordinator：

T1: TaskGroup-1: useSize = 2, availableSize = 1
  - 等待队列：Task-4, Task-5

T2: Master-A 的 TaskGroupCoordinator 扫描：
  - 发现 availableSize = 1
  - 分配槽位给 Task-4（优先级更高）
  - useSize = 3（已满）

T3: Master-A 的 TaskGroupCoordinator 下次扫描：
  - 发现 availableSize = 0
  - Task-5 继续等待

结果：
  - 并发数严格控制在 groupSize = 3
  - 资源控制有效
  - 数据一致性保证
```

#### 事件处理流程

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/cluster/AbstractClusterSubscribeListener.java:28`

```java
@Override
public void notify(Event event) {
    try {
        // 确保事件按顺序处理
        synchronized (this) {
            Event.Type type = event.getType();
            T server = parseServerFromHeartbeat(event.getEventData());
            if (server == null) {
                log.error("Unknown cluster change event: {}", event);
                return;
            }
            switch (type) {
                case ADD:
                    log.info("Server {} added", server);
                    onServerAdded(server);
                    break;
                case REMOVE:
                    log.warn("Server {} removed", server);
                    onServerRemove(server);
                    break;
                case UPDATE:
                    log.debug("Server {} updated", server);
                    onServerUpdate(server);
                    break;
                default:
                    break;
            }
        }
    } catch (Exception ex) {
        log.error("Notify cluster change event: {} failed", event, ex);
    }
}
```

**处理逻辑详解：**

1. **ADD 事件：节点加入集群**
   ```
   触发条件：
     - 新的 Master 注册到 Zookeeper
     - TreeCache 监听到节点创建
   
   处理流程：
     a. 解析心跳数据，创建 MasterServerMetadata
     b. 调用 onServerAdded()
     c. 添加到内存缓存（masterServerMap）
     d. 通知所有监听器
     e. 触发 Slot 重新平衡
   ```

2. **REMOVE 事件：节点离开集群**
   ```
   触发条件：
     - Master 节点被删除（会话超时或主动删除）
     - TreeCache 监听到节点删除
   
   处理流程：
     a. 解析心跳数据，创建 MasterServerMetadata
     b. 调用 onServerRemove()
     c. 从内存缓存移除
     d. 通知所有监听器
     e. 触发 Slot 重新平衡
     f. 触发 Failover 事件（延迟 30 秒）
   ```

3. **UPDATE 事件：节点信息更新**
   ```
   触发条件：
     - Master 心跳数据更新
     - TreeCache 监听到节点数据变化
   
   处理流程：
     a. 解析心跳数据，创建 MasterServerMetadata
     b. 调用 onServerUpdate()
     c. 更新内存缓存
     d. 通知所有监听器
     e. 如果状态变化（NORMAL ↔ BUSY），触发 Slot 重新平衡
   ```

### 7.4 集群状态监控

#### ClusterStateMonitors

**代码位置：** `dolphinscheduler-master/src/main/java/org/apache/dolphinscheduler/server/master/cluster/ClusterStateMonitors.java:32`

```java
@Component
public class ClusterStateMonitors {
    
    @Autowired
    private ClusterManager clusterManager;
    
    @Autowired
    private SystemEventBus systemEventBus;
    
    public void start() {
        // 注册 Master 移除监听器
        clusterManager.getMasterClusters()
                .registerListener((IClusters.ServerRemovedListener<MasterServerMetadata>) this::masterRemoved);
        
        // 注册 Worker 移除监听器
        clusterManager.getWorkerClusters()
                .registerListener((IClusters.ServerRemovedListener<WorkerServerMetadata>) this::workerRemoved);
        
        log.info("ClusterStateMonitors started...");
    }
    
    void masterRemoved(final MasterServerMetadata masterServer) {
        // 延迟 30 秒，给 Master 重连的机会
        systemEventBus.publish(MasterFailoverEvent.of(masterServer, new Date(), 30_000));
    }
    
    void workerRemoved(final WorkerServerMetadata workerServer) {
        // 延迟 30 秒，给 Worker 重连的机会
        systemEventBus.publish(WorkerFailoverEvent.of(workerServer, new Date(), 30_000));
    }
}
```

**延迟原因：**
- **网络抖动**：可能导致短暂断开
- **30 秒内如果 Master 重连**：可以跳过 Failover
- **避免不必要的容错操作**：减少系统开销

**延迟机制：**

```
Master-A 节点被删除
    ↓
ClusterStateMonitors.masterRemoved()
    ↓
发布 MasterFailoverEvent（延迟 30 秒）
    ↓
30 秒内：
  - 如果 Master-A 重连，节点重新创建
  - Failover 事件检查到节点存在，跳过容错
    ↓
30 秒后：
  - 如果 Master-A 仍未重连，执行容错
```

## 总结

### 核心机制总结

#### 1. 服务注册机制

**特点：**
- 使用 EPHEMERAL 节点，自动创建父节点
- 注册前等待服务状态为 NORMAL
- 注册后验证节点是否存在
- 启动心跳任务定期更新

**优势：**
- 服务下线时自动清理节点
- 其他节点实时感知服务状态
- 无需手动管理节点

#### 2. 脑裂防护机制

**特点：**
- 断开连接时主动停止服务
- EPHEMERAL 节点自动删除
- 分布式锁选举 Active Master

**优势：**
- 避免脑裂问题
- 保证数据一致性
- 防止脏数据

#### 3. 心跳机制

**特点：**
- 两层心跳（底层会话心跳 + 应用层数据心跳）
- 应用层心跳包含服务器状态、资源使用等
- 状态改变时立即更新

**优势：**
- 实时反映服务器状态
- 支持负载保护（BUSY 状态）
- 其他节点可以基于心跳数据做决策

#### 4. 容错机制

**特点：**
- Zookeeper 事件监听（主要机制）
- 数据库查询（全局容错）
- 延迟 30 秒执行（避免网络抖动）

**优势：**
- 自动检测节点故障
- 自动触发 Failover
- 防止重复容错

#### 5. 去中心化设计

**特点：**
- Slot 机制实现负载均衡
- 所有 Master 地位平等
- 自动重新平衡

**优势：**
- 无单点故障
- 自动负载均衡
- 可扩展性强

#### 6. 单例协调

**特点：**
- MasterCoordinator 选举 Active Master
- 只有 Active Master 运行 TaskGroupCoordinator
- 管理全局资源（TaskGroup）

**优势：**
- 避免资源冲突
- 保证数据一致性
- 统一管理全局资源

#### 7. 集群管理

**特点：**
- 实时监听集群变化
- 内存缓存节点信息
- 监听器模式通知变化

**优势：**
- 快速响应集群变化
- 自动触发相关操作（如 Slot 重新平衡）
- 提供查询接口

### 设计优势

1. **高可用**
   - 无单点故障
   - 自动容错
   - 快速恢复

2. **负载均衡**
   - Slot 机制自动分配任务
   - 任务均匀分配到各个 Master
   - 自动重新平衡

3. **数据一致性**
   - EPHEMERAL 节点 + 主动停止服务
   - 分布式锁保证原子操作
   - 容错标记防止重复操作

4. **可扩展**
   - 动态添加/移除节点
   - 自动重新平衡
   - 无需手动配置

5. **实时感知**
   - 事件驱动
   - 快速响应集群变化
   - 无需轮询
